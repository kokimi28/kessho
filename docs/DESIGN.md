# KESSHO — 設計書 v1.0

## 1. モジュール構成

```
kessho/
  docs/          STRATEGY.md / REQUIREMENTS.md / DESIGN.md（正本）
  data/          stream.json（差分粒子ストリーム・extract の出力）
  src/
    lib.mjs      純ロジック層（DOM/canvas 非依存・node:test 対象）
    app.js       アプリ層（canvas 描画・入力・画面遷移。lib のシンボルを前提）
    style.css    夜間単一テーマ（試作の設計トークンを継承）
    body.html    アプリの DOM 骨格
  scripts/
    extract-stream.mjs   git 履歴 → data/stream.json
    build.mjs            src + data → dist/index.html（完全自己完結）/ dist/artifact.html
    test.mjs             node:test（依存ゼロ・ネットワーク不要）
  dist/          ビルド成果物（リリース物）
```

- **lib と app の境界**: 乱数・凝集・投影・日次集計・訪問状態・文言生成など「答えが一意に決まる計算」はすべて lib。app は描画とイベントのみ。テストは lib に集中させる（brypo-landing の `scripts/*.mjs` 文化と同型）。
- ビルドは文字列インライン（`export` を剥がして `<script>` に連結）。実行時依存ゼロ・CDN なし。

## 2. 視覚系の確定事項（試作第一〜四.五稿の判断記録）

| 判断 | 内容 | 根拠 |
|---|---|---|
| 比例表現 | 1コミット=1粒・半径=log₂(1+行数)・誇張なし | 「階層は過剰表現」の判定。正直さ=信用 |
| 銀河式立体 | 枝は平面 DLA（枝ぶりの美）＋枝に沿う z うねり＋面内自転＋傾きカメラ | 純球 3D DLA は 270 粒で泡塊化（実測棄却） |
| 熱 | 着弾夜が最も明るく7日で冷える。冷えた粒は硝子＋時折きらめき | ストック（美）とフロー（変化）の分離 |
| 意味の字幕 | 着弾ごとに「リポ ← 種別 +n行」、終幕に総行数カウントアップ | 「何がどう変わったか」をデータ自身に語らせる |
| HUD は canvas 内 | 日付・粒数・スクラブ・字幕・総括を描画パイプライン内に統一 | 環境差の排除（headless 検証で DOM 下部描画の不確実性を確認）＋管制室の美学 |
| 六層合成 | 地の光→結晶脈→粒子輝体→彗星残光→衝撃波/火花→全体ブルーム | 「芸術性で圧巻」要求への回答 |

## 3. 決定論の規約（定点観測の成立条件）

- seed は固定値（`20260729`）。形は入力列（日付昇順の stream）にのみ依存。
- 明日の粒は必ず今日の形の続きに堆積する（既存粒の再配置はしない）。
- スクラブ・創世・夜報再生はすべて「可視粒数の前置換表 `cumByDay`」で表現（再計算しない）。
- 実行時の `Date` 使用は「観測記録（訪問日）」のみ。描画は全て入力データの日付を使う。

## 4. 観測記録（localStorage）の状態機械

キー `kessho:v1` = `{first,last,visits,streak,seenEvents,seenLines}`。遷移は純関数 `updateVisitState(prev, today, events, lines)`:

- prev なし → 初期化（streak=1・catchup なし）。
- 同日再訪 → visits+1・streak 維持・catchup は前回保存分との差分。
- 翌日 → streak+1。2日以上空き → streak=1（結晶側は無傷）。
- catchup = seenEvents との差分（>0 のときだけ着弾再生の対象）。

## 5. データ更新とリリース経路

- **v1.0（本リリース）**: スナップショット埋め込みの静的1ファイル。配布は Artifact URL（即時）→ 👤 が `kessho` リポ生成後、Cloudflare Pages/Vercel の静的ホスティング＋独自ドメイン。
- **v1.1（夜間自動化・リポ生成後）**: GitHub Actions（毎晩 JST 23:45）が extract → `data/stream.json` 更新 → build → Pages デプロイ → かけら画像＋機械文を X へ（brypo-landing の publish/OAuth1.0a 資産を移植）。人間の作業ゼロ。
- **v2（Layer3・別設計）**: 「あなたの結晶」= GitHub OAuth → ユーザー別 stream 抽出 → 同一エンジンで描画。課金線。DB が初めて必要になる（Neon 想定）。本 v1 のエンジンは表示層としてそのまま使う。

## 6. 検証戦略

- 純ロジック: `node --test scripts/test.mjs`（依存ゼロ）。決定論の回帰は座標チェックサムで固定。
- 実機: headless Chromium で3画面＋オープニングをスクリーンショット検証（ウィンドウ高は十分に取る——下端タイル未描画の headless 既知事象があるため）。
- 手動確認観点: 着弾のリズム／スクラブの追従／タブ切替時の描画停止・再開／localStorage 消去時の初期化。

## 7. 意味ズーム（v1.2・地図の文法）

オーナー判定「奥行きがない・見たいところが定まらない」への回答。地図の「県→市→駅」を移植した。

| 縮尺 | 見えるもの | 対応 |
|---|---|---|
| 遠景（z<1.85） | 事業ラインの地名（税ツール・SaaS…） | 県 |
| 中景（1.35<z<3.8） | リポ名（交差フェード） | 市 |
| 近景（z>2.9） | 大きな差分（≥1,000行）の標識 | 駅 |

- **地名タップ＝飛行**: カメラの焦点（3D 点）とズームが目標へ補間される。焦点は回転する結晶上の点を追い続ける（軌道カメラ）。ダブルタップで一段引く。パンくず（全景 › 税ツール › tedori-calc）が現在地。
- 帯域は純関数 `lodBand`（台形アルファ・テスト対象）。ズーム上限 7。z<1.2 に引くと自動で全景に帰着。
- 奥行き強化: 透視 F=CR×1.7・霧 0.42–1.0・遠景の星層 80 点（自転で結晶と視差がつく）。

## 8. 突入（v1.3・中に入る）

「切り替えではなく中に入る感覚」への回答。画面遷移を捨て、すべてをズーム深度への連続写像にした。

- **通過の物理**: 投影 k をカメラ極近で有限にクランプし、k>2.1 の粒は巨大化しながらフェードアウト＝粒の間を抜けて進む感覚。
- **部屋化**: リポ焦点で z>4.2 から突入開始。部屋の外の粒・脈は diveAlpha に比例して霧に沈む。
- **機能一覧**: そのリポの全仕事（日付・種別・行数・件名）が半透明パネルとして底から滲み出る。不透明度 = f(ズーム深度)。行タップで該当粒が共鳴。ダブルタップで部屋の外へ（3.4）→ 以降は階層を一段ずつ戻る。
- リポ地名の二度目のタップ＝突入（zoomT 5.6）。初回タップ時に「もう一度タップで中に入る」の字幕で誘導。

## 9. 形の文法 v1.4 — 枝＝リポの年表（DLA の廃止）

オーナー判定「繋がり・関連性が見えず、粒が適当に置かれてる感」への回答。DLA（確率的凝集）は有機的な見た目と引き換えに**位置の意味を捨てていた**ため廃止し、全部の位置に意味を与えた:

- **方位 = 事業ライン**（ライン内でリポごとに扇割り）
- **1 本の枝 = 1 リポ**。コミットを**古い順に根元→先端へ数珠つなぎ**（隣の粒＝時間的に隣のコミット）
- **枝の長さ = 歴史の量**・**先端 = 最新**（熱で光るのは常に先端）・今夜の着弾は必ず枝の先端に付く
- 枝はリポ固有の巻き癖（seed 決定論）でシダの若葉状に湾曲。奥行きは枝に沿って波打つ
- `parent[i]` は「同リポの直前コミット」= 結晶脈が本物の年表の線になり、共鳴はそのリポの歴史を遡って走る
- 実装 `buildBranches`（lib）。DLA `buildCluster` は非構造クラスタ用に残置。形状チェックサムは branches-v1 で再凍結

## 10. 山頂ビューと道（v1.5・押す場所の明確化）

オーナー判定「粒が伸びていると、どこを押したらいいか分からない」への回答（PS2 の入り込みアニメーション参照付き）。

- **山頂カメラ**: 全景は真上からの俯瞰（tilt≈-0.10）で、枝＝道が全円に放射して見える。ズームインに連動してカメラが斜めへ倒れ（→-0.78）、円柱状の奥行きの中へ潜る。`tiltForZoom`（純関数）。
- **道 = タップ目標**: 遠景では枝に太い路盤を敷き、枝のどこを押してもそのリポへ入場（zoomT 5.6 へ直行）。粒を正確に押したときだけ検分・共鳴（優先順位: 精密粒 → 地名ラベル → 道）。
- **突入スピードライン**: ズーム速度に比例した放射ストリーク26本（PS2 的トンネル演出・reduced-motion では出ない）。
- **部屋の陳列**: 突入先はまず数字（最新の夜・直近7日・通算/稼働夜・アクセス枠=計測接続後）→ 仕事の構成バー → 8週の律動 → 全仕事一覧、の順に陳列。`repoStats`（純関数・テスト対象）。

## 11. ステーション（v1.6・人工衛星の連結）

オーナー判定「粒自体が微妙。明確に部屋化してドアから入る感じ」への回答。形の主役を「粒の連なり」から**構造物**へ:

- **モジュール = リポ**: 中央ハブから放射するトラスにドッキングするカプセル。長さ=コミット数（34–150）・幅=行数の log（15–30）。
- **窓 = コミット**: 船体軸に時系列順の千鳥配置（窓の並び=年表・熱で点灯・着弾は船体に着く）。creation リプレイ=窓が時間順に灯る建造映像。
- **ドア = ドッキングポート**: ハブ側の暗い円窓。**昨夜更新のあったモジュールのドアは琥珀色に脈動**（検分の案内）。モジュールのどこを押してもドアから中へ（既存の潜行＋陳列の部屋）。
- 実装 `buildStation`（lib・純関数・テスト: 窓が船体内にあること/年表連結/決定論）。チェックサム station-v1 で再凍結。旧 `buildBranches` はかけら用に残置。

## 12. 環状線ダイアグラム（v1.7・ベックの原理）

オーナー判定「ステーションに見えない・大きさばらばらで規則性がない・文字が小さく薄い・面白いポイントが伝わらない。世の中の例え方を調べて参考に」への回答。調査に基づく設計転換:

- **参照した実例**: ハリー・ベックのロンドン地下鉄路線図（1933）——地理的正確さを捨て、均一間隔の駅・限定角度・電気回路図の様式で判読性を得た原理。および、ゲームのステージ選択画面の定石（均一ノード・状態バッジ・増加耐性）。
- **均一の原則**: 駅（=リポ）は全て同径のポッドで環上に等間隔。**データ量は形でなくバッジと数字で語る**（比例表現は窓の粒径にのみ残す）。
- **環状線**: ライン＝路線色の弧（同ラインの駅は隣接配置）。駅名は常時・明るく表示（横方向の駅は上下配置で画面内に収める）。
- **ハブ＝今夜のヒーロー数字**: 中央に「7月29日の夜業 +1粒 +1行」——面白いポイントを最前面に。
- **バッジ**: 昨夜更新の駅に琥珀「+n」。未検分なら脈動。
- **窓＝フィロタキシス**: ポッド内にひまわり螺旋（黄金角）で全コミットを年代順充填（自然界の規則充填＝均一かつ有機）。
- 操作簡素化: 階層は「全景 ⇄ 駅の中」の2段のみ。駅タップ=入場・ダブルタップ=退出。自転は 0.03 rad/s に減速（操作感）。
- 実装 `buildRing`（lib・テスト: 駅が環上・ライン非分断・窓がポッド内・年表連結・決定論）。チェックサム ring-v1。

## 13. 心理・ユーザビリティ監査（v1.8・最終磨き）

全フロー監査で7点を修正:

1. **現在地ピン留め**（オーナー指摘）: 部屋にいる間、上部に「駅色ドット＋駅名＋ライン＋昨夜バッジ」を固定表示。
2. **見える出口**: ピンバーに「× 退出」ボタン（隠しジェスチャ＝ダブルタップだけに依存しない）。
3. **案内の文脈連動**: 検分 HUD を「琥珀バッジの駅に入って検分」（全景）⇄「光る枠の窓をタップ」（部屋内）に切替。部屋内はピンバーの下に表示。
4. **全景静止**: 路線図は動かないから覚えられる（空間記憶・Fitts）。自転 0、ドラッグ回転は遊びとして残す。
5. **字幕の可視保証**: 突入中は字幕を画面上寄り（H×0.30）へ移動しパネルと重ねない。
6. **儀式の逓減対策**: 同日再訪（差分なし）はオープニングを省略し即入場＋昨夜の着弾のみ。
7. **初回の一手案内**: 初訪問のみ「駅をタップすると中に入れる」を一度だけ表示。

見送り（次版候補として記録）: ブラウザ戻るボタンでの退出（pushState 化）／駅名の斜め方向衝突の完全回避／部屋内の窓とリストの双方向ハイライト。
